# GTA giveaway leaderboard
This is distinct from Zs, the existing random giveaway system, and Kick's rolling Active Chatter List.
Each stream has non-overlapping 30-minute blocks anchored to Kick's start timestamp. A normal eligible message qualifies its account once in that block. Commands, the host, known bots, and anonymous chat do not count. The exact block boundary belongs to the next block; incomplete blocks do not count. Only campaign-time events are captured. The first block can be joined after the campaign opens only if coverage can be verified. Qualifying check-ins from earlier streams persist. Ties display tied ranks; a tied winner must be resolved by the published contest rules, not alphabetical display order.
The database stores Kick account ID, handle, time and block, not chat content. The board returns handle, rank and score only. A healthy scheduler observation (verified incoming-chat subscription and official channel state) advances verified time. A known observation gap, repaired chat subscription, or unconfirmed end is handled conservatively. No event-source check guarantees delivery of every single chat message. Admin starts the campaign, freezes it at the end, and can mark a participant who passed; the prize is assigned manually. Nothing changes Zs.
## Release gate and smoke test
1. Apply the migration in staging. Test signed chat + live start/end and confirm the existing trivia/webhook path is unaffected. Verify the scheduler runs normally with consecutive healthy observations at most 150 seconds apart.
2. Set `GTA_GIVEAWAY_ENABLED=1` only in the target environment after migration and only with an approved public launch. It is off by default. The signed lifecycle subscription is checked and registered without removing the existing chat or reward subscriptions.
3. Publish the eligibility, tie-break, no-purchase rule, and prize details before starting a real campaign. The signed-in owner alone can start/stop/mark passed at `/#/gta-giveaway`. Check the published page from an unauthenticated browser.
4. Use a staging or announced test stream to confirm: repeated messages give one point; a boundary message belongs to the next window; offline messages give no points; another stream carries standings forward. Stop only after the final included checkpoint. End the campaign manually after production acceptance. Do not advertise it until the live data path has been verified.
5. Turn off the feature flag to stop collection without deleting standings. On recovery, suspected missing blocks must not be reconstructed from viewer counts. A plain cron snapshot of a chatter list is not a substitute.
